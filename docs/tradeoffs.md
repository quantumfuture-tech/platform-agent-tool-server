# 换来了什么，付出了什么

## 换来了什么

1. **确定性**：同一份规则 + 同一份记录，输出逐字节相同。演示、回归测试、对账都靠这一条。
2. **可审计**：每条结论都有 rule 与 inputs。用户问「为什么」，不需要模型回忆，直接调 explain。
3. **可测试**：规则是数据，边界可以单测。0.15 与 0.35 这两个边界现在有测试兜着。
4. **模型可替换**：工具协议是唯一接口面，换一个模型只影响「怎么问」，不影响「怎么算」。
5. **复用**：同一套工具可以同时服务对话智能体、网页、批处理脚本，不必为每个入口重写一遍规则。

## 付出了什么

1. **多一层服务**：要部署、要监控、要处理端口与错误。纯提示词方案没有这一层。
2. **协议要维护**：openapi.yaml、校验逻辑、响应字段三处必须同步；字段改名就是一次兼容性变更。
3. **规则变更要发版**：改阈值要改数据文件并重启（或做热加载）。提示词改一行就能上线，这里不行。
4. **多一跳延迟**：一次对话可能串 2 到 3 个工具调用，每个都要走网络与 JSON 解析。
5. **对话体验受工具粒度限制**：工具切得太细，模型要串很多步；切得太粗，参数又难填。五个工具是这次选的折中。
6. **合成数据验证不了真实业务**：这套骨架证明「结构能跑通」，不证明「真实培养方案一定这么算」。

## 什么时候不该这么做

- 一次性问答，没有复用与追责需求；
- 规则天天变、且没有版本管理能力；
- 没有运维能力，连一个 Node 进程都不方便托管；
- 数据本身不允许离开模型上下文（这种情况下要先解决数据边界，而不是先写工具）。

## 刻意没做的事

这个仓库是骨架，不是产品。以下都故意留白：

- 鉴权、限流、多租户；
- 持久化（记录从请求体来，或读内置合成文件）；
- 真实教务数据接入；
- 大模型调用代码（模型在平台侧，不在这个仓库里）；
- 前端页面。

留白不是遗漏：接口面越小，越容易看清「模型只负责对话」这条主张。
